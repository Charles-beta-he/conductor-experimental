# M3 — fixed-DAG execution composition (local experiment)

User authorization: latest direct request `推进主任务`. This is a new bounded composition milestone toward the original standalone conductor goal, not an extension/reset of M2 review. M2 SPEC and all frozen r1/M2 implementation bytes stay unchanged. This document is canonical only for M3.

## Objective and chosen path
Connect the existing proposal-only planner to the existing durable attempt Store through public APIs. Demonstrate a real two-task dependency chain across fresh Python processes. Choosing a separately packaged synchronous composition layer avoids inventing a platform lifecycle owner or duplicating M2 attempt storage. No new runtime adapter or model/provider calls are needed: M2 already has a real Python runtime.

Success is bounded fixed-plan dispatch -> candidate -> independent deterministic verification -> downstream dispatch -> all-verified local projection. This is not the complete conductor product or general semantic evaluation.

## Contracts
- Flow takes an immutable tuple of Binding(Task, Request, attempt_id), a concrete M2 Store, and a caller-selected adapter registry (identity -> trusted adapter). All tasks are pre-submitted by the trusted host under explicit M2 Grants. Flow never creates grants, submits tasks, reconciles, cancels, retries, replans, adopts workers or writes ACP lifecycle.
- Every tick preflights the WHOLE binding set before any adapter/verification call: strict types, valid DAG, duplicate task/attempt rejection, exact request/task/adapter/attempt binding to fresh Store.query rows. Missing/wrong binding or adapter fails closed, including a bad downstream binding. Do not trust caller-supplied status or cached VERIFIED.
- PREPARED rows are omitted from the planner observation projection; attempts_used counts started (not PREPARED reservations). Maximum attempts equals the fixed plan task count. The separate Store owns durable global starts/concurrency budgets; neither fresh Flow construction nor a new drive invocation resets those budgets.
- UNKNOWN preempts all work; RUNNING is observed, not declared dead or adopted. Candidate requires a separate verify tick. Dispatch only the planner's ready PREPARED task via Store.run; each tick invokes at most one run OR verify. Store.run remains the authorization/claim/final-dispatch gate. Flow has no alternate direct adapter call path.
- A complete projection requires fresh Store.query validation of every VERIFIED artifact. If prior dependencies are now UNKNOWN while downstream observations exist, return conservative reconcile_required rather than reinterpret this as a valid DAG snapshot or continue execution. CANDIDATE cannot satisfy dependencies. CANCELLED halts.
- Each drive(max_ticks) accepts strict int 1..1024; each iteration is one tick. Stop on accepted_projection, reconcile_required, halt or wait; after consuming the invocation cap return tick_budget_exhausted. Reopening/another invocation is explicit host action, not an automatic retry. This is a per-invocation decision bound, NOT a durable lifetime decision budget or wall-clock deadline. Each M2 execution retains its persisted timeout/output/start/concurrency bounds. Trusted adapters may still block outside their contract; no OS sandbox claim.
- Flow bindings are immutable in-memory host-owned data, not an authenticated/durable plan SSOT. The demo records the exact task/request/attempt/adapter/dependency binding in an exclusively created private JSON file and reconstructs it in later fresh interpreters. The library does not discover tasks from a private DB schema, deserialize adapter code, accept model-selected commands, or promise concurrent mutable-plan support. A Flow instance is synchronous; overlapping hosts rely only on M2's existing claim fencing and may get conservative wait/errors, not a cross-task serialized scheduler guarantee.
- Return structured local decisions and step records distinguishing submitted/running/candidate/verified observations. `accepted_projection` is a local fixed-plan observation, never certified/production acceptance.

## Non-goals / boundaries
No mutable plans/replan budgets, automatic failure retries, durable outbox, multi-host ownership, new ACP lifecycle, scheduler/gateway/profile changes, real provider calls, release/push/deploy, arbitrary Hermes revision support, live tool-denial certification, hostile local filesystem/DB or adapter sandbox. M2 U1/U2 remain unchanged.
